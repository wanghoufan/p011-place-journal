## 4. 正常演化与新出现的产品认识

- 从 Web 到 Android 双端共用同一 Supabase 是合理扩展；真正的成本在「双端照抄」而非双端本身。
- AI 确认与可撤销私密快照分享是产品亮点，属正常演进。
- 微信拦外链导致分享动线改为「出图优先」——外部平台行为第一天可查证，属可预防而非纯迭代。
- 分支分叉（10-02）与合并（`7a1ebd2`）属正常 Git 演化，但源于仓外开发纪律缺失。

## 5. 计划者原本应前置发现的缺口

- 价值探针：语音输入、封面 OCR 这类 AI 能力是否真的需要、耗时是否可接受。
- 外部依赖预算：Vercel 15s 限制、微信外链拦截、PWA 图标与签名要求。
- 端策略：先 Web 还是先 Android、是否共用 Schema、双端同步语义。
- 资源前置：密钥备份、签名证书、真机与 ROM、图标资产。
- 验收资产化：每次验收写产物 md5、真机安装、分享第一产物是图。

## 6. UI / 操作模式可复用经验

- 首屏画廊＋三入口＋悬浮记录，是「私人手账」的低摩擦记录动线，可复用。
- 记录流程「拍照/说感受 → AI 确认 → 可撤销分享」把 AI 放在确认位而非生成位，降低不可控性。
- 分享必须默认私密、可撤销；第一产物是图（兼容微信拦外链）。
- 图标/启动图要在每个版本验收，不能只看功能存在。
- 名字一旦定下要统一到 README、SSOT、工作区名与 Schema 注释，否则长期误导（本项目四套名字）。

## 7. 外部条件、测试资源与正式部署条件

- 硬阻塞：Supabase 项目与密钥（须仓外备份）、签名证书、真机（双 ROM）。
- 开发者自办：同步语义矩阵、幂等与 revision、分支与工作区纪律。
- 可延后：多端更多、更多 AI 能力、公开分享。
- 验收才需：双机安装与图标对照、分享链路真机验证、产物 md5 记录。

## 8. 下次同类项目 Day 1 就应确认

- 名字：不是打卡工具，`habit_tracker` 只是历史 Schema 名。
- 同步：逐项列出界面写操作的幂等键/revision/顺序依赖，并规定删除不复活、回写不覆盖、冲突可裁决。
- 输入与 AI：先验证输入方式；所有 AI 可等待、可跳过、失败可手填、超时不丢记录。
- 交付：唯一工作区/分支、每次验收写产物 md5、签名与升级规则当天定、分享第一产物是图。

## 9. 适用范围与反例

- 适用：私人记录类双端应用（手账、旅行、收藏、照片日志）。
- 不适用：真正的习惯养成产品（streak/周期/提醒是核心，本结论不适用）。
- 反例提醒：不能因为本项目「不用打卡」就推断所有个人工具都不需要周期性功能。
- 「AI 放在确认位」适用于输入不可控场景；纯生成型产品需另设评估口径。

## 10. 责任划分与下次做法
